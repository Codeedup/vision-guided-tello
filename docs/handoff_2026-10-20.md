## Validated software revision and changes

- Validated code commit: `e88bd164a754b6a2ee9368f08dc996f3db57bda7` (`Freeze target loss audit and capture running ROS provenance`). The checkout was clean when runtime provenance was captured. This handoff is a documentation-only successor to that validated code revision.
- [Target-loss analyzer](../tools/analyze_target_loss.py) now accepts a one-hand ineligibility transition immediately preceding tracking loss, followed promptly by a no-hand observation. It rejects a multiple-hand transition as removal evidence. Tracking source freshness remains **strictly less than 250 ms**; the 250 ms receipt association allowance is for passive observer scheduling, not a runtime safety-limit change.
- The analyzer accepts the bridge's independent `APPROVED_INPUT_LOSS` watchdog as the first landing cause only when it is paired to the loss timing. It still rejects unrelated or early faults. After hand return, it allows up to one second of reacquisition flicker before counting **five uninterrupted seconds** of eligible hand with the landing latch held and no restart. The audit records its policy version and the analyzer's SHA-256.
- [Runtime provenance capture](../tools/runtime_provenance.py) is called by the [pipeline launcher](../tools/start_webcam_pipeline.py) when `--provenance-output` is supplied. Before `READY`, it requires a clean checkout, ROS package prefixes in this workspace, and exactly one running installed process for each required node. It records PIDs, command lines, installed paths and hashes, interpreter paths, and hashes of compiled running executables. A mismatch stops startup. The [commissioning runbook](commissioning_runbook.md) includes this option.
- [Analyzer regressions](../tools/tests/test_target_loss_analysis.py) and [provenance regressions](../tools/tests/test_runtime_provenance.py) cover misleading ordering, exact freshness boundaries, interrupted absence, brief return flicker, watchdog timing, and wrong/missing/duplicate executables.

This count includes test wrappers, not 519 distinct flight behaviors. The validated revision was rebuilt after commit. Hosted CI has **not** been verified for `e88bd16` in this handoff.

## What remains before any real movement command

1. **Choose one real SDK command owner and route.** The current Windows diagnostic owns Tello SDK/video during camera tests; WSL runs FAKE ROS. There is no commissioned ROS-to-real-Tello movement gateway. Decide between a Windows gateway or a separately proven all-WSL route. Never run competing SDK clients.
2. **Define independent manual takeover.** Identify what the human pilot will use if the laptop, ROS process, or Wi-Fi link fails. A FAKE `takeover` state only revokes software authority; it does not establish that the physical pilot can control the Tello.
3. **Build and bench the guarded command path with propellers off.** Keep the aircraft grounded. Verify socket ownership, bounded channel mapping, neutral on stale/lost commands, battery/telemetry rejection, link-loss behavior, shutdown, and attempted send versus SDK reply. Do not infer motion or landing from an SDK `ok` or height alone.
4. **Then plan controlled physical stages.** With a charged/inspected aircraft, appropriate area, and pilot ready to take over, establish a current manual baseline. Verify one axis and its actual sign, neutral response, and override before any hand-guided motion. Real battery, critical fault coverage, and physical stop/landing response remain unverified.

Codex can do the code, offline tests, manifests, command-path design, and log review. The user must provide and supervise the aircraft, select/verify the physical takeover method, and pilot or supply a pilot for any propeller-on trial. No user action is needed to interpret the existing FAKE traces.
